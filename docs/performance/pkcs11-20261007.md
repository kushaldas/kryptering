# PKCS#11 module lifetime benchmark — 2026-10-07

## Build and workload

Baseline: kryptering 0.6.0 commit
`1cb2c1d64a5ecf78bb0d69abaac22e19d30081c2`, with only the benchmark example added.
Candidate: local 0.6.1 working tree implementing ADR 0004. Both compiled with
`cargo build --release --example pkcs11_lifetime`, default features, the same
Cargo.lock dependencies (only kryptering's own version changed). No downstream
pybergshamra dependency was changed. This is a local workstation test, not the
remote aggregation server or Luna.

The benchmark uses an existing dedicated SoftHSM 2.6 RSA-2048 test key. It runs
20 iterations per fresh process, each constructing a provider by token label,
opening/logging into a session, looking up signer and verifier objects, signing
and verifying the 29-byte string `kryptering lifetime benchmark`, and dropping
all caller handles. There are two initialized tokens and one uninitialized slot.
No token reset, key provisioning, or production credential was involved.

Five fresh processes per build. The baseline executable was preserved at
`/tmp/kryptering-pkcs11-baseline-060` before implementation. Raw CSV, process timing
and filtered loader traces are in [pkcs11-20261007/](pkcs11-20261007/).

## Results

| Metric | Baseline | Candidate | Interpretation |
| --- | ---: | ---: | --- |
| Module opens for 20 cycles | 20 | 1 | Separate LD_DEBUG trace; timings exclude tracing |
| Median warm provider construction | 1,870 µs | 126 µs | 93.3% lower; iterations 1–19, pooled over five processes |
| Median complete cycle | 6,945.5 µs | 4,748.5 µs | 31.6% lower; includes signing and verification |
| Median complete process elapsed | 0.16 s | 0.11 s | 31.3% lower; `/usr/bin/time` has 0.01 s precision |
| Median peak RSS | 9,432 KiB | 9,564 KiB | +132 KiB; per-process peak |
| Median first provider construction | 12,438 µs | 7,517 µs | Cold samples vary; do not attribute this difference solely to caching |

Each signature was verified. Sessions still close on every iteration; PIN
handling, already-logged-in rejection and per-use RSA modulus validation are
unchanged. The candidate also removes duplicate token-info queries during
label selection, so these numbers measure the combined change.

These are sequential before/after runs on a shared workstation, not randomized
trials. Small absolute differences and cold timings are noisy. Retaining a module
eliminates repeated loader work but cannot eliminate the first initialization
of a fresh process. This workload intentionally recreates providers; applications
already retaining one provider will not receive the same improvement.

There is no Luna measurement here and no claim to fix its reported 20-second
wait. That requires per-call elapsed timing on the vendor module.

## Commands

```sh
cargo build --release --example pkcs11_lifetime
export SOFTHSM2_CONF=/home/kdas/code/xml/pybergshamra/hsm-test/softhsm2.local.conf
export HSM_BENCH_MODULE=/usr/lib/softhsm/libsofthsm2.so
export HSM_BENCH_TOKEN=pybergshamra-test
export HSM_BENCH_KEY=test-rsa-key
export HSM_BENCH_PIN=1234  # public dedicated fixture PIN only
/usr/bin/time -f 'elapsed_s=%e maxrss_kib=%M' \
  target/release/examples/pkcs11_lifetime
```

Repeat five times per executable. To confirm loader activity, run separately:

```sh
LD_DEBUG=files target/release/examples/pkcs11_lifetime > /tmp/hsm.csv 2> /tmp/hsm-loader.log
```

Count `opening file=` lines naming the configured SoftHSM module. ELF init/fini
messages are not PKCS#11 initialization/finalization call counters. The cache's
unit tests separately verify that concurrent callers invoke the initialization
closure once, retain it after caller handles drop, and retry failed initialization.
